# Kun 的办公室模型

[English](office-model.md) · [项目概览](../README.zh-CN.md)

我的精力有限，设备里的 agent 越来越多以后，我希望管家能联络各个办公室，把结果汇总成需要我做的决定，
不用我一直盯着每条线程。virtual-bot-connect 放的是这个思路和我围绕它搭的方案。

## 组网与管家

已验证的例子里，Grok Bot 提供一台虚拟机电脑，通过 Tailscale 和本地设备连成私人网络。
它既是私人管家，也是我想要的总经理：接目标、联系对应办公室、跟进，再收集结果。
组网和叫醒设计参考了郭宇老师的 [Yobiru](https://github.com/chekusu/yobiru)。Yobiru 提供 agent 之间的通信，任务怎么管理还需要另外安排。

## 设备、员工与工作中枢

一台设备是一个**办公室**，在里面工作的 agent 是**员工**，使用该设备上的文件和已获准的权限。
这个例子里，**Multica** 是工作中枢和账本，负责派活、保存记录；管家负责联络、汇总和汇报；老板给目标，做需要人拍板的决定。

我的判断是，看板、多 agent、远程 App 还是把跨线程协调这件事留给了我，所以我希望有一个总经理。
这是我对自己工作方式的判断，不是说这些工具对所有人都没有协调作用。

办公室按设备划分，项目按业务划分。塔罗、toB、自媒体、学校是我想留下知识的方向，列出这些名字不代表每个方向各有一台已经跑通的设备。
更多办公室之间的协作，是从本地设备和云电脑这个已验证例子向外扩展的模型。

## 记忆与备份状态

员工做完任务后，把有用的决定和经验留进项目记忆。这些记录是我希望带进下一个办公室、交给下一位总经理的资产。
留痕回答发生过什么，项目记忆留下下一位员工需要知道的东西。

| 项目 | 计划怎么做 | 当前状态 |
|---|---|---|
| Grok Bot 记忆备份 | 每 **2 天**自动备份到 Google 云盘 | **进行中**，尚未验收通过 |
| Multica 记忆备份 | 每 **7 天**自动备份到 Google 云盘 | **进行中**，尚未验收通过 |
| 换办公室、换总经理 | 从保留的项目记忆和备份继续工作 | 设计目标，完整恢复未验证 |

这里写的是计划中的备份周期，不是已经完成的自动化；仓库也没有备份安装器或恢复成功的证据。
此前「每天导出到私有仓库」的建议由这里的状态取代。任务有结果、Multica 有记录，都不能证明 Google 云盘备份已经运行。

## 验证范围

- **已验证**：Grok Bot 用 CLI 直连 Multica、Multica 叫醒 agent、本地设备通过 Tailscale/SSH 访问 Grok Bot 云电脑，以及[脱敏例子](../examples/kun-mac-multica-grok/)中的执行信箱通路。
- **实测中**：Multica → Grok Bot 的 webhook 叫醒。服务端做好不代表 Bot 已叫醒或工作已完成，送达、叫醒、完成仍分别记录。
- **未测**：Dots、Muse、Cue、独立的 Claude Code/Codex/OpenCode/Pi 桥接，以及在本方案里用 Yobiru 当传输层。可考虑替换不等于已支持。
- **进行中**：上表的 Google 云盘备份周期。恢复与搬家仍是目标。

## 办公室之间的连接部件

[信箱、叫醒、权限、全程留痕](primitives.md)连接管家和员工。网络连通不代表获得了项目或钥匙的访问权；
先草稿和权限规矩继续适用，保留记忆也不代表新 Bot 自动获得旧的授权和钥匙。

要适配新的环境，先读[能力清单](adding-a-new-bot.md)，再看[可选接入手册](../AGENTS.md#a-setup-playbook)。
与 Yobiru 的对比见[注明版本的研究笔记](../research/yobiru.zh-CN.md)。
